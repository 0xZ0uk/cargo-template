# Changelog

## [Unreleased]

### Added

- Rich text as Markdown (#67), from a new entry `./mcp` (so the plugin never imports `@payloadcms/plugin-mcp`, now an optional peer): `setRichTextFromMarkdown`, a plugin-mcp collection tool (`defineCollectionTool`) that converts Markdown with the field's own editor (`field.editor.converters`) and writes it as the user, as a draft by default, after approval; data paths into groups, arrays and blocks (`layout.3.columns.0.content.1.richText`, blocks resolved by `blockType`), updating the top-level field with ids intact; clear errors that list the document's rich text paths. It refuses to drop formatting Markdown can't keep (underline, alignment, indentation, internal or new-tab links, upload/relationship/block nodes) unless `allowFormattingLoss: true`, and says when the field's editor kept some of the Markdown as plain text (a heading level or lists it doesn't allow). `richTextAsMarkdown(slug)`, an `overrideResponse` for `findDocuments` that returns rich text as Markdown (external MCP clients included). `withMarkdownRichText(slug, entry)` adds both to a collection's plugin-mcp entry.
- The approval card of `setRichTextFromMarkdown`: the field's text before (current value as Markdown) and after (the proposed Markdown as the field will store it), with a notice for formatting that would be lost or Markdown the field doesn't support.
- System prompt: rich text rules (read as Markdown, write only with the Markdown tool, never Lexical JSON in create/update, what is lost) when the app installed the tool; read drafts with `draft: true` when discussing or editing a draft (#116).
- `testModel` (tests only, #66): turns answered by a scripted `fakeText()` model instead of OpenRouter, with no key and no network (`src/server/testModel.ts`): `/tool <name> <JSON>` in a message calls that tool, a tool result gets `Tool <name> finished: …`, a rejection gets "The change was rejected. Nothing was written.". Only requests made to a loopback host use it (`usesTestModel`): elsewhere a turn still needs `apiKey` (503 without), so a deployed Worker can't be switched to it. It reaches the Durable Object as `settings.testModel`, set by the endpoint. `GET /api/assistant/config` adds `testModel: true` when it applies, so a test can check it never talks to OpenRouter.
- Registered in `apps/web` (#66): Durable Objects declared through Wrangler's `exports`, the `ASSISTANT_SELF` service binding, a Workers Rate Limiting binding on `rateLimit`, and Playwright specs on the test model.

- Approval cards with a diff before any write (#65). `GET /api/assistant/approvals?threadId=` builds a proposal per pending interrupt, read as the user: update (field-by-field against the current document), create (the proposed fields), delete (what will be lost), restore version, duplicate, by-`where` batches; rich text converted from Lexical to readable text (`src/approvals/lexical.ts`), never JSON. `ApprovalCard` is the new default `ApprovalComponent`, rendered in place of the write's tool row, and keeps the outcome after sending: applied, rejected (with the reason) or failed with the error (access errors at apply time included).
- Reject with a reason: the resume payload `{ approved: false, reason }` becomes the reject branch of the tools' `approvalSchema` (`REJECT_APPROVAL_SCHEMA`), which `chat()` returns to the model as the denied call's result. Approvals no longer accept edited arguments.
- Several approvals in one turn are answered card by card (with Undo) or with Approve all / Reject all, and sent as one batch, since TanStack resumes a batch all or nothing.
- Stale proposals: `changedSinceProposal` when the document changed after the interrupt (the card asks to confirm again), and `seenUpdatedAt` on approve: a document changed since the card showed it refuses the resume with `409 { code: "stale", interruptIds }`.

### Fixed

- Approval diffs of arrays and blocks (#113 review): rows pair by id (rows without one by position), a removed row is labelled `(removed)` with its position before so it can no longer share a path or label with a kept row, a new row with no values is still reported, and a reordered row shows a `Position` change instead of an empty diff.
- "Approve all" and each Approve are disabled until every pending change has loaded, so nothing is approved unseen or without the `updatedAt` its diff was built from; a change whose diff couldn't be loaded asks "Approve anyway?" on its own card and blocks Approve all; after a stale refusal the old diff is replaced by a loading state until the fresh one arrives (#113 review).
- A send refused before the run started (rate limited, `model_not_allowed`, not configured) no longer leaves its bubble in the transcript (#112 review).
- A successful delete no longer links to the edit views of the deleted documents (#112 review).
- The approval input is no longer cut silently: the diff card shows values whole and scrollable and says when one was shortened; `ApprovalControl` says so too (#112 review).
- The composer at 390px: Send stays on the model picker's row, the hint goes under them (#112 review).
- `pendingApprovalFrom` finds the tool call of a `generic` interrupt in its binding (`@tanstack/ai-client`'s snapshot drops `toolCallId`).

- The chat view at `/admin/assistant` (#64), from a new client entry `./client` (`"use client"` added after the build, as in `payload-plugin-ab`; no server or workerd code). `useChat` (`@tanstack/ai-react` 1.0.2) over SSE with `persistence: true`: opening a conversation hydrates it, restores pending approvals and rejoins a run still going (a reload mid-reply picks the stream back up); Stop calls `POST /api/assistant/chat/stop`. The open conversation is in the URL (`?thread=`).
- Messages: Markdown through `@tanstack/ai-react/ui`'s `TextPart` (`@tanstack/markdown`, already a dependency of `ai-react`: raw HTML escaped, executable URLs dropped, no new package); the user's own text stays plain; reasoning collapsed; each tool call a compact row (tool, collection, status) with its result collapsed and bounded, and links to the documents it returned or touched (only in collections/globals the admin knows, never from free text). Model-written links to admin pages navigate in place; other links open in a new tab without an opener.
- Composer: multi-line, Enter sends, Shift+Enter adds a line (IME-safe), Stop while streaming, model picker from `GET /api/assistant/config` (remembered per browser). Disabled with a reason while not configured or while an approval waits.
- Conversation list: new, switch, inline rename, delete after Payload's `ConfirmationModal` (deleting the open one starts a new one). Narrow screens toggle the list above the chat.
- Errors inline as Payload `Banner`s, from `RUN_ERROR` codes and HTTP `{ code }` bodies (`fetch` wrapped to keep the body `@tanstack/ai-client` drops): not configured, invalid key, out of credits, rate limited, model unavailable, context overflow, signed out, forbidden, tools unavailable, not found, stopped. A refused send puts the text back in the composer.
- Approvals: a minimal approve/reject control (`ApprovalControl`) per pending interrupt, swappable through `AssistantChat`'s `ApprovalComponent` prop and `PendingApproval` (#65's diff card goes there). The browser has no tool definitions, so `@tanstack/ai-client` binds approvals as `generic` interrupts; they are answered with `{ approved }`.
- The nav link, `admin.components.afterNavLinks` → `./admin/AssistantNavLink`: a server component that asks the same `access` as the view and renders nothing for anyone it refuses (or if it throws).
- Tests: jsdom component tests (Markdown safety, tool rows, composer keys, approvals, conversation list) and the error/link/result helpers; the nav link's access gate against real Payload next to the view's redirects.

- The chat turn (#63), `createTurnRunner()` in `src/server/turn.ts`: `chat()` on OpenRouter (`createOpenRouterText(model, apiKey, { appTitle, httpReferer })`, SDK retries off) with plugin-mcp's tools as the admin, the conversation's stores (`withPersistence`), compaction past `maxContextTokens` (old tool results first, then the oldest turns), `maxIterations(maxSteps)`, prompt caching (`session_id` = thread, Anthropic cache markers) and the camelCase provider routing. Tests assert the serialised request body (`provider: { require_parameters, data_collection: "deny" }`).
- `AssistantConversation` runs that turn by default (the 501 stub is gone). The Worker endpoint authenticates, validates, resolves the turn's settings (model, key, system prompt, limits, `toolFilter` names) and hands the turn to the object, proxying its SSE. A closed tab doesn't stop a run.
- Stop: `POST /api/assistant/chat/stop` / `ConversationBackend.stop()`. The run's `chat()` is aborted, the stream ends with `RUN_ERROR { code: "stopped" }` (in the log too, so a rejoin sees it) and the run is `aborted`. Deleting a conversation still cuts its run at once (`RunControl`).
- Endpoints for the admin UI (#64), contract in the README: `POST /api/assistant/chat` (turn or approval resume, `useChat`-compatible body), `GET /api/assistant/chat` (rejoin with `Last-Event-ID`/`?offset`, or the `hydrate()` transcript), `POST /api/assistant/chat/stop`, `GET|PATCH|DELETE /api/assistant/conversations[/:threadId]`, `GET /api/assistant/config`. JSON errors carry a `code`.
- System prompt built on the Worker: the site, its collections and globals with the descriptions given to plugin-mcp, drafts-first and never publish unless asked, `getCollectionSchema` before writing, small targeted updates, a link to the admin page after a change, then the app's `instructions` and `payloadToolsSystemPrompt`.
- OpenRouter errors mapped to `RUN_ERROR` codes with user-facing messages: `openrouter_invalid_key` (401), `openrouter_out_of_credits` (402), `openrouter_rate_limited` (429), `model_unavailable` (404/502/503, "no endpoints"), plus `context_overflow`, `not_signed_in`, `tools_unavailable`, `stopped`, `run_failed`.
- The transcript is server-authoritative: only the request's newest user message is used (text only, 32,000 characters at most, given a stable id); earlier or non-user messages from the client are ignored. A new conversation is titled from its first message. Hydration includes `runs` (`completed` / `aborted` / `failed`).
- Options: `maxContextTokens` (default 64,000) and `appTitle` (OpenRouter attribution).

### Fixed

- OpenRouter's 400 "… is not a valid model ID" (a retired or misspelled id in the allowlist) maps to `model_unavailable`, not `run_failed`.

### Changed

- `inProcessDispatch`, `mcpEndpointFor` and `payloadToolSourceForRequest` moved to `src/tools/inProcess.ts`, so the Durable Object bundle never imports `payload`.
- `rateLimit(req)` is called for chat turns (send and resume) only; reads, rejoins, stop and the conversation endpoints aren't rate limited.

- Payload tools (#61), `src/tools/payloadToolSource.ts`: `createPayloadToolSource({ endpoint, headers, dispatch, toolFilter })` gives `chat({ mcp })` plugin-mcp's tools as the signed-in user, through an MCP client that forwards the admin's `Cookie`/`Authorization`/`Origin` to `POST /api/mcp`. The dispatcher is injectable (`McpDispatch`): `inProcessDispatch(config)` runs the request through `handleEndpoints` in the same isolate; a Durable Object can pass a service-binding fetch instead. `payloadToolSourceForRequest(req)` wires it for a `PayloadRequest`.
- Tool rules: plugin-mcp's auth tools and `getUploadInstructions` (the model can't upload bytes) are never offered; `toolFilter` applies on top. Tools not annotated `readOnlyHint: true` need approval. Access denials reach the model as tool errors, not retries.
- Discovery fails loudly: `AssistantNotSignedInError` when `/api/mcp` doesn't accept the session (`-32601` from `tools/list`), `AssistantToolDiscoveryError` otherwise; `payloadToolsMcpOptions(source)` rethrows them from `onDiscoveryError`, so a run never goes ahead with no tools.
- `payloadToolsSystemPrompt(instructions)`: tool guidance for the system prompt, chiefly `select` + `limit` + `depth: 0` on `findDocuments`.
- Conversations in Durable Objects (#62), exported from `./do` (workerd-only): `AssistantConversation` (one per conversation: messages, runs, interrupts, metadata and a `StreamDurability` log over its SQLite; runs the chat turn so a run outlives its request) and `AssistantConversationIndex` (one per user: `SessionIndexStore` for list/rename/delete). Both pass `runPersistenceConformance` under workerd.
- Ownership: the first `claim` owns a conversation; reads, rejoins, new turns, renames and deletes by anyone else answer like a missing conversation. The object re-checks the owner on its own routes.
- Retention: an alarm deletes conversations idle for `conversations.retentionDays` (default 30) with their index entry. Size caps (`conversations.caps`): tool results cut to 16 KiB, oldest whole turns dropped past 400 messages or 1 MiB, stream-log events shrunk below 256 KiB.
- `ConversationBackend` for the endpoint (#63): Durable Objects, or `memoryConversations()` in Node. Turns run through a `TurnRunner` with the capped persistence, an MCP `fetch` and a stop signal.
- MCP from inside the object: `serviceBindingMcpFetch` over a service binding to the same Worker (`ASSISTANT_SELF`), forwarding the admin's Cookie and Origin; prototyped under workerd against a real MCP server.
- Options: `conversations: { namespace, index, retentionDays, caps }` (`namespace` and `index` go together).
- Deleting a conversation during a live run aborts the run and fences it off (an epoch per purge): its last events, rows, activity and alarm never land in the deleted conversation, and readers tailing it end.
- A run id is rejected (409) for the conversation's whole lifetime, also after its stream log was pruned (`assistant_run_ids`, plus the runs table).
- `conversationBackend()` rebuilds the memory backend on every call with that call's options, over one process-wide set of conversations (`createMemoryConversationState()`, `memoryConversations({ state })`); the first caller's options no longer stick.
- Tests: a workerd suite (`vitest.workerd.config.ts`, `@cloudflare/vitest-plugin` 1.4.11) run by `pnpm test` after the Node suite.

- Package scaffold (#60): `assistantPlugin(options)` registers `POST /api/assistant/chat` and the `/admin/assistant` view. The endpoint checks sign-in (401), `access` (403), configuration (503), `rateLimit` (429), then answers `501 { error: "not implemented" }`; the view is a placeholder. No collections, globals or fields, so no migration and no import-map change beyond the view.
- Options: `enabled`, `access`, `models`, `defaultModel`, `apiKey`, `instructions`, `maxSteps`, `toolFilter`, `conversations: { namespace }`, `rateLimit`. A missing `apiKey` warns and leaves the assistant unconfigured: the endpoint and view are registered either way and report "not configured".
- Access: `access({ user, req })` guards both the endpoint (403) and the admin view (redirect to `admin.routes.unauthorized`; anonymous visitors go to login). The default admits only users of the admin auth collection (`config.admin.user`), not any signed-in user, so a session on another auth collection can't spend OpenRouter credit or reach the admin shell. The function reaches the view through `serverProps` only, never the client config.
- OpenRouter provider routing defaults (`requireParameters`, `dataCollection: 'deny'`), camelCase on purpose.
